# 긴 PDF 자동 탐색·추출 입력 준비

2026-09-16. 이전 40페이지 자동 파서 병목을 문서 전체 상한과 보관 상한으로 분리했다.
자동 조사 뒤 입력을 추가하지 않고 동작하며, 모델 호출은 추가하지 않는다.

## 구현

- 자동 문서 경로만 최대 200페이지, 10페이지씩 텍스트 탐색한다. 수동 PDF 경로의 기존 40페이지 한도는 유지한다.
- 각 묶음은 기존 항목/문자 제한을 적용한다. 누적 비공백 span 80,000개/문자 1,000,000개,
  파서 40초/문서 요청 55초/다운로드 5MB 제한을 유지한다. 상한을 넘기면 성공 결과를 발행하지 않는다.
- 용량·안전성·반응·분석집단·통계 문구의 존재를 신호로 사용한다. 빈도 점수가 아니고 같은 점수면 원본 페이지 순이다.
  묶음마다 우선순위와 자원 한도에 맞게 최대 40페이지/20,000 span/250,000자를 보관한다.
  스트리밍 문구 선택 정책이며 최적 문서 선정·임상 적합성 판단이 아니다.
- `lexical-pages/1`은 총 페이지, 탐색/보관/미보관/텍스트 없는 페이지, 선정 신호를 기록한다.
  원본 SHA-256, 원본 페이지 번호 및 `p42-i78` 같은 span ID를 그대로 유지한다.
- `pdf-evidence-window/1`은 희소한 원본 페이지를 담는 별도 형식이다.
  기존 연속 페이지 `pdf-evidence/1`로 위장하거나 페이지를 1부터 다시 매기지 않는다.
- 화면은 전체/보관 수, 후보, 펼칠 수 있는 페이지 범위를 표시한다. 내보내기에 조사 ID/출처 URL도 포함한다.
  스캔 이미지 OCR·표 구조·수치·임상 의미를 검증했다는 표시는 없다.

## 실제 검증

기존 조사 `07438cdb-8633-4d11-b857-39d4b466f8ce`의 실제 저장 PDF를 로컬 문서 API로 읽고,
실제 PDF.js 파서 → 자동 페이지 선정 → 후보 및 입력 생성 함수를 실행했다.
브라우저 새 조사 전체 실행은 아니며, 두 문서를 각각 격리해 점검했다. 일반 자동 실행은 첫 준비 성공 시 종료한다.

| 문서 | 텍스트 탐색 | 보관 | 후보 원본 페이지 | 입력 span | 결과 |
| --- | ---: | ---: | --- | ---: | --- |
| NCT04933695 SAP_005 | 43 | 40 | 21, 10, 12 | 15 | READY |
| NCT04933695 Prot_004 | 123 | 40 | 31, 42, 11 | 15 | READY |

둘 다 캐시 HIT, 텍스트 없는 페이지 0, 추가 모델 호출 0회.
로컬 단일 실행 약 0.36초/0.70초이며 브라우저 성능 보장값이 아니다.
프로토콜 보관 범위에는 원본 119·122페이지도 포함됐다. 앞 40페이지 절단이 아니다.
초기 진단은 Origin 헤더 누락으로 403이었다. 기존 로컬 경계 설정에 맞춰 재검사했으며 서버 검증을 완화하지 않았다.

신규 합성 검사 9개: 늦은 페이지/원본 ID/범위 분할, 빈 텍스트, 수동 경로 유지,
200페이지 경계, 취소/정리, 누적 문자 제한, 보관 문자 제한, 오류 정리, 세션 형식·지문.
웹 전체 815개 통과 및 TypeScript/Vite 빌드 확인. Python 변경 없음, 직전 606개 통과 기록 유지.
Chrome에서 기존 첫 화면/동의·저장 이력 표시를 확인했으나 새 READY 범위 펼치기·모바일 시각 QA는 아직이다.

## 아직 남은 연결

준비 입력과 페이지 범위는 탭 및 JSON에만 존재한다. 원본은 기존 로컬 DB에 남는다.
기존 프로젝트/필드 검토 계약은 연속 40페이지를 가정하므로 window 형식을 자동 주입하지 않는다.
다음 작업은 **희소 페이지 원본 위치 검증·저장/복구·뷰어 연결 → AI 추출 인계**다.
이어 같은 시험·코호트/표 단위·각주 확인 → 필요한 쟁점만 사람에게 요청 → 설계 계산을 연결한다.
추출 후보 준비는 임상 필드 추출 성공도, 전체 설계 자동 완주도 아니다. 전체77%/기업25% 추정 유지.
