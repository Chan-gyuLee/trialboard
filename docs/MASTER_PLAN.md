## 1 제품의 중심

TrialBoard는 표적항암제 개발팀이 용량 비교 임상시험을 준비할 때 사용하는 근거 기반 설계 검토 작업공간이다. 첫 사용자는 용량 최적화 또는 규제기관 미팅을 준비하는 바이오텍 임상개발 책임자로 가정한다. 실제 사용처와 지불 의사는 인터뷰로 검증해야 한다.

고객의 시작 질문은 “이 약물의 다음 용량 비교시험을 어떻게 설계하고, 그 결정을 뒷받침할 자료는 무엇인가?”다. 약물명만 넣으면 정답을 주는 챗봇이 아니라, 검토 범위와 결정 질문을 입력하고 회의에 가져갈 설계 검토 패키지를 만드는 제품이다.

입력은 약물·시험 ID, 적응증·환자군, 개발 단계, 검토 질문, 자료 기준일, 공개자료 또는 허용된 입력자료다. 범위는 단일 경구 표적항암 소분자 단독요법의 용량 증량 이후 Phase Ib/II 용량 최적화다. 첫 본선 버전은 공개자료만 사용한다.

최종 결과는 하나의 연결된 패키지다.

1. 근거 검토표: 무엇이 어느 문서·환자군·시점에서 관찰되었는가.
2. 설계 비교표: 최소 두 후보의 목적·용량군·평가변수·선택 규칙·장단점은 무엇인가.
3. 시뮬레이션: 명시한 가정이 달라지면 선택 결과와 위험이 어떻게 달라지는가.
4. 전문가 검토 브리프: 어떤 판단이 남았고 누가 어떤 자료를 확인해야 하는가.

최적 용량, 승인 확률, 임상 성공률이나 환자별 처방은 제공하지 않는다. 논문 검색에서 멈추지 않되, 공개 근거가 허용하지 않는 임상 결정을 자동으로 확정하지 않는다.

## 2 대회와 사업을 연결하는 전략

본선의 성과물과 판매 제품을 서로 다른 방향으로 만들지 않는다. 같은 근거 검토 패키지를 본선에서는 재현성과 오류 검출로 증명하고, 기업에서는 회의 준비와 재확인 시간을 줄이는지 검증한다.

차별화 가설은 “자료가 많다” 또는 “에이전트가 많다”가 아니다. **다른 시험·환자군·버전의 근거가 섞여 생기는 설계 오류를 줄이고, 설계 조항까지 추적 가능하게 만든다**는 것이다. 이 가설은 기준선 비교로 검증해야 하며 경쟁 제품보다 우월하다고 미리 주장하지 않는다.

초기 판매 방식은 특정 약물·검토 질문에 대한 유료 파일럿을 제안한다. 검수 가능한 산출물과 데이터 사용 범위를 합의한 뒤, 반복 수요가 확인되면 지속형 도구 또는 기업 내부 AI팀 구축 협업으로 확장한다. 유료 계약이나 외부 연락은 별도 사용자 요청 없이 실행하지 않는다.

## 3 사용자 화면

사용자 피드백을 반영한 현재 첫 흐름은 **자료 → 내용 확인 → 검토 질문 → 쟁점과 원본 → 다음 행동**이다. 현재 상단 메뉴는 자료 검토, 가정 실험, 공개 근거, 실험 기록이다. 가정 실험을 먼저 보여주어 입력과 결과의 관계를 혼동시키지 않는다. 아래는 이후 연결할 제품 영역이며 현재 모든 기능이 완성된 화면 목록은 아니다.

| 영역 | 사용자가 하는 일 | 반드시 보이는 정보 |
| --- | --- | --- |
| 근거 | 핵심 사실과 충돌 검토 | 시험·코호트·버전·단위·분모·발화 주체 |
| 설계 비교 | 후보와 가정 변경, 계산 비교 | 근거 기반 조항과 가정 기반 조항의 구분 |
| 검토 보고서 | 수정사항·미해결 질문 검토와 내보내기 | 담당 역할·필요 자료·판단 재개 조건 |
| 원문 패널 | 선택한 주장 확인 | PDF 페이지·위치 또는 구조화 데이터 경로 |

실행 진행 상황은 보조 영역에 둔다. 도구 호출, 작업 상태, 간결한 판단 근거와 비용을 보여주되 모델의 내부 사고과정을 실시간 출력한다고 표현하지 않는다. 사용자에게 중요한 것은 에이전트 간 대화가 아니라 결정과 근거다.

PDF 좌표는 추출 엔진, 페이지 크기, 회전, 원점과 함께 보존하여 브라우저의 하이라이트 좌표로 변환한다. 원문 클릭만 성공하는 것이 아니라 정확한 표·문맥이 열리는지를 테스트한다. 내보내기는 같은 결과 데이터에서 생성하는 인쇄용 HTML과 JSON부터 시작하고, 본선 보고서 PDF를 연결한다.

## 4 기술스택 결정

아래는 구현과 확장 계획을 함께 정리한 표다. 현재 설치된 핵심은 React·TypeScript·Vite·MUI/Emotion, Python 3.12·FastAPI·Pydantic·NumPy·pdfplumber다. SQLAlchemy/DB, LLM adapter, PDF.js, BM25, SciPy, SSE, Docker, GitHub Actions, Playwright는 아직 구현하지 않았다. 현재 테스트는 pytest와 Node 함수/계약 테스트다. 원격 백엔드·저장소 선택은 배포 환경과 데이터 권한을 확인한 뒤 확정한다. 의존성은 lockfile로 관리한다.

| 영역 | 선택 | 선택 이유와 제약 |
| --- | --- | --- |
| 프런트엔드 | React + TypeScript + Vite | 근거표·원문·설계 비교를 다루는 웹앱. 검색 노출·서버 렌더링이 핵심이 아니므로 Next.js는 우선 제외 |
| UI 구성 | MUI + Emotion + 업무용 CSS (구현) | Material Design 기반의 외부 라이브러리이며 Google 공식 컴포넌트는 아님. 사용성·접근성 실검증과 디자인 확정은 남아 있음 |
| 백엔드 | Python 3.12 + FastAPI + Pydantic 2 | 데이터 처리·통계·API를 한 언어로 구성. 입출력 스키마와 OpenAPI 활용 |
| 실행 관리 | 명시적 Python 상태기계 | 허용 도구·예산·재시도·종료를 통제. 초기에는 LangChain·LangGraph를 필수 의존성으로 두지 않음 |
| LLM 계층 | 공급자 교체 가능한 얇은 adapter | 대회 제공 API의 실제 기능을 연결 시험한 뒤 모델·구조화 출력 방식 확정. 평가 결과로 역할별 모델 선택 |
| 저장 | SQLAlchemy 2 + SQLite WAL + 스키마 이력 | 본선은 단일 인스턴스·제한된 동시 실행. 외래키·트랜잭션·원본 불변성 강제 |
| 원본 자료 | hash 기반 파일 스냅샷 + manifest | 재현성과 권리 메타데이터 보존. 운영 데이터는 영속 볼륨에 저장 |
| PDF | pdfplumber 추출 + PDF.js 뷰어 | 문자·표·위치를 추출하고 브라우저에서 원문 확인. 실제 주요 문서로 추출 품질 선검증 |
| 검색 | 시험·문서 메타데이터 필터 + BM25 | 작은 공개 근거집합부터 시작. 검색 평가에서 필요가 확인될 때 임베딩 추가 |
| 계산 | NumPy + SciPy, 고정 seed | LLM이 산술하지 않음. 가정별 계산과 오차·재현성 검증 |
| API 통신 | REST + SSE | 실행 시작·결과 조회와 진행 이벤트 분리. 저장된 이벤트 ID로 재연결 |
| 테스트 | pytest + 프런트 단위 테스트 + Playwright | 데이터 규칙, 계산, 원문 이동, 세 실행 예제의 회귀 검증 |
| 개발·배포 | uv + 프런트 lockfile + Docker + GitHub Actions | 재현 가능한 빌드. 서비스 하나와 영속 저장소로 시작 |

FastAPI의 타입 기반 검증·API 명세는 [공식 문서](https://fastapi.tiangolo.com/), Vite의 React·TypeScript 템플릿 및 실행 조건은 [공식 가이드](https://vite.dev/guide/)를 기준으로 한다. SQLite 외래키는 연결마다 활성화가 필요하므로 [SQLAlchemy 문서](https://docs.sqlalchemy.org/en/20/dialects/sqlite.html#foreign-key-support)를 구현 체크리스트에 넣는다.

### 상용화를 고려한 PDF 선택

기존 PyMuPDF는 AGPL 또는 별도 상용 라이선스로 제공된다. 상용 사용이 무조건 금지된다는 뜻은 아니지만, 폐쇄형 기업 납품을 염두에 두면 라이선스 조건 검토가 필요하다. 초기안은 MIT 라이선스인 pdfplumber와 PDF.js를 우선 평가해 이 의존성을 줄인다. 스캔 PDF는 별도 OCR 없이는 지원 범위 밖으로 표시하고, 원문 표를 안정적으로 읽지 못하면 수동 확인 또는 보류로 남긴다. 전체 의존성과 문서 재배포 권리도 별도로 점검한다. [PyMuPDF 공식 안내](https://pymupdf.io/pymupdf), [pdfplumber 공식 저장소](https://github.com/jsvine/pdfplumber), [PDF.js](https://mozilla.github.io/pdf.js/).

### 처음부터 넣지 않을 것

Neo4j, 전용 벡터 DB, Redis·Celery, Kubernetes, 모델 fine-tuning, 대규모 OCR, RDKit 기반 화학 분석, 다중 기업 SaaS, 모든 암종 지원은 초기 범위에서 제외한다. 본선의 “근거 그래프”는 관계형 DB의 노드·관계 모델로 구현할 수 있다. 약물 식별은 이름·시험 ID·구조화 식별자 매핑부터 검증하고 화학 분석으로 범위를 넓히지 않는다.

기업 파일럿에서 동시 쓰기·여러 서버·고객 분리 요구가 생기면 PostgreSQL과 객체 저장소로 이동한다. 이는 URL만 교체하면 끝나는 작업이 아니므로 데이터 이관, SQL 차이, 권한과 회귀 테스트를 포함한다.

## 5 핵심 데이터와 실행 구조

### 근거와 결정의 연결

자료 계층은 SourceVersion → EvidenceSpan → Claim → DesignClause로 연결한다. 하나의 주장에 여러 근거를 붙일 수 있도록 ClaimEvidence 관계를 둔다. SimulationRun은 실제 Claim에서 가져온 입력과 별도로 Assumption을 참조한다. ReviewIssue는 영향을 받는 주장·설계 조항과 필요한 추가 자료를 가리킨다.

SourceVersion에는 URL·hash·수집일·문서일·작성자를, Claim에는 시험·적응증·코호트·치료군·투여 일정·평가변수·분모·분석 시점·발화 주체를 저장한다. LineageEdge에는 관계 유형뿐 아니라 그 관계를 지지하는 근거를 붙인다. 날짜의 정확도가 월 단위면 그대로 보존한다.

초안 Claim과 탈락한 Claim도 감사 기록에는 보관한다. 다만 검증을 통과하지 못한 내용을 채택 근거로 사용하지 못하게 한다. “저장됨”, “원문에 존재함”, “주장을 지지함”, “사람이 확인함”을 서로 다른 상태로 관리한다. 모델의 자체 판정만으로 전문가 검증 완료 상태를 만들지 않는다.

### 다섯 역할과 통제된 자율성

근거탐색, 임상설계, 통계설계, 반론검토, 인용검증의 다섯 역할을 유지한다. 역할마다 별도 상시 실행 서비스가 필요한 것은 아니다. 상태기계가 적절한 도구와 역할을 호출하고, 각 결과를 스키마와 검증 규칙으로 검사한다.

정상 흐름은 수집 → 정규화 → 후보 설계 → 계산 → 검토다. 충돌이 발견되면 필요한 문서만 추가 검색하고, 수정할 수 있으면 설계나 근거를 갱신한다. 추가 탐색·수정은 초기 상한 2회로 제한하고 설정과 실행 로그에 남긴다. 도구 호출 수·시간·비용 한도를 함께 둔다.

자동 검증 완료 초안, 부분 보류, 기술적 실패, 사용자 취소를 구분한다. 사람의 최종 승인은 별도 기록이다. 일부 값이 없다는 이유로 전체 작업을 폐기하거나, 완료 표시를 위해 없는 값을 생성하지 않는다.

### 실행 복구와 보안

API 요청은 run을 생성하고, 별도 실행 worker가 저장된 작업을 처리한다. 본선에서는 실행 동시성을 제한하고 대기 상태를 표시한다. SSE 이벤트와 단계 산출물을 DB에 저장하여 브라우저 새로고침이 실행을 잃게 하지 않는다. worker 재시작 시 중복 실행을 막을 claim·lease와 재실행 가능한 단계 경계를 둔다. 무거운 계산은 API 응답을 막지 않는 작업 경로로 분리한다.

공개 데모는 예산 제한·요청 빈도 제한·허용 출처를 두며 임의 URL 수집과 기업 기밀 업로드는 열지 않는다. 원문을 다운로드하는 도구는 사설 IP·내부 주소 접근을 차단해야 한다. API 키는 서버에만 두고 원문 내 지시문을 실행 명령으로 취급하지 않는다. 일반 로그에 비밀키나 민감한 원문을 기록하지 않는다.

모든 재현을 비트 단위 일치로 약속하지 않는다. 원문·저장 결과 재생과 고정 계산은 재현하고, 모델을 다시 호출한 실행은 결과가 달라질 수 있음을 표시한다. 실시간 수집, 스냅샷으로 모델 재실행, 저장 결과 재생은 별도 실행 모드다.

### 세 실행 예제와 확장성의 구분

## 7 검증을 제품의 일부로 구현

개발용 5개 사례와 독립 평가 10개 이상 사례·200개 이상 원자적 항목이라는 제안서 목표를 유지하되 달성 여부를 구분한다. 초기 50개 항목은 중간 점검이다. 두 관련 전문가의 독립 주석과 합의가 목표이며, 확보하지 못하면 전문가 검증 미완성으로 명시한다. 팀원이라는 이유만으로 전문가 자격을 가정하지 않는다.

일반 검색·단일 LLM+RAG·전체 시스템의 검토시간과 오류를 비교한다. 모델·자료·예산을 가능한 한 맞추며, 편리하게 실패한 기준선만 고르지 않는다. 이력·인용 검증·반론 단계를 제거한 실험으로 복잡한 구조가 실제 이득을 주는지 확인한다.

핵심 지표는 채택 주장의 정확성, 치명적 단위·분모·코호트 오류, 충돌·결측 검출, 적절한 보류, 검토자의 총 준비·재확인 시간이다. 주장별 정확도만 아니라 답변 비율과 오류 목록도 보고한다. 계산에는 고정 seed, 알려진 기준값, 극단 조건과 Monte Carlo 오차 검증을 붙인다.

## 8 기존 코드의 처리

사용자의 명시적인 요청으로 이전 수집·이력·저장·CLI 구현과 관련 테스트·PLAN을 제거했다. 현재 검토 경로는 이전 구현을 import하지 않는다. 필요한 해시 기능은 `serialization.py`로 독립시켰으며, 사용하지 않는 의존성도 정리했다.

복구 기준은 `f19ea73ff5eecb20b089ea4626514865015a5768`이고 Git 이력은 보존했다. 원본 제안서와 실제 원문 스냅샷은 삭제하지 않았다. 기존 기능을 모두 대체한 것은 아니며, 자동 수집·실시간 API·LLM 역할은 새 데이터 계약에 맞춰 구현할 예정이다.

## 9 역할과 바로 다음 작업

권장 분담은 AI 개발 지원이 구현·회귀 테스트·실험 자동화·UI 연결을 맡고, 두 팀원이 자료 판정·임상 질문·발표·사용자 검증을 전문성에 맞춰 나누는 방식이다. 실제 전문가 판정과 고객의 지불 의사는 코드 생성으로 대체할 수 없다. 이 문서가 팀원의 전문성이나 참여를 확정한 것은 아니다.

다음 구현 작업의 목표는 기능 모듈 수를 늘리는 것이 아니라, sotorasib 질문 하나에 대한 “사람이 받아보고 쓸 수 있는 최종 검토 보고서”의 데이터 계약과 테스트를 확정하는 것이다. 핵심 근거 약 20개를 원문과 연결한 작은 검토집합을 만들고, 그 입력으로 전체 흐름을 연결한다. 이 집합은 개발용이며 독립 평가 정답과 분리한다.
