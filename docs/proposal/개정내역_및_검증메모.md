# TrialBoard 제안서 개정내역 및 검증 메모

2026년 9월 11일 제안서 초안 작성 시점의 검토 기록이다. 이후 사용자의 요청으로 이전 Claude Code 구현을 삭제했으므로, 아래 코드 평가는 당시 commit에 대한 역사적 기록으로 읽어야 한다. 현재 상태는 `../PROGRESS.md`를 따른다. 원본 HWPX는 보존했으며 제안서를 공식 제출하지 않았다.

## 이번 개정의 판단

제안의 강점은 표적항암제 용량 최적화라는 좁은 문제, 시험별 근거 이력, 계산과 언어모델의 분리, 전문가 승인 구조다. 이를 유지하면서 “무엇을 실제로 납품하고 어떻게 검증하는가”를 구체화했다. 전문가의 실제 평점·평가 사유는 공개되지 않았으므로, 위 강점이 본선 진출 원인이라는 설명은 추정이지 확인된 심사평이 아니다. 공개 피어 점수로 전문가 점수를 역산하지 않았다.

개정 후에는 과장 위험과 내부 불일치가 줄고 심사 질문에 대한 답이 명확해진다. 다만 문서 개선만으로 심사점수 상승, 우승, 계약 또는 임상적 성능을 보장할 수 없다. 특히 세 예제의 실행 완결성과 독립 평가 결과가 아직 필요하다.

## 추가된 코드에 대한 평가

검토 기준 commit: `f19ea73`. 실행한 확인: `.venv/bin/python -m pytest -q` → 6개 통과. 이는 해시·기초 스키마·스냅샷 중심의 단위 테스트로, 제품 전체 성능이 아니다. 이번 문서 작업에서 아래 코드는 수정하지 않았다.

좋은 기반은 출처 스냅샷과 hash, 구조화 스키마, SQLite 저장, 실제 PDF 인용 위치를 연결하려는 구현이다. 특히 `trialboard/corpus/seeds.py`는 ODAC 172698 자료를 Amgen 신청자 자료로 구분한다. 이 기반을 버릴 이유는 없다.

다음은 본선 전에 우선 고칠 정확성 문제다.

1. `trialboard/core/schemas.py`, `trialboard/graph/store.py`: claim에 span ID가 있다는 것과 해당 span이 실제 존재하는 것은 다르다. 빈 인용, 없는 span, 잘못된 source 연결을 거부하는 저장·검증 규칙과 테스트가 필요하다.
2. `trialboard/lineage/builder.py`: PMR 문장 앞부분의 문자열 일치로 더 긴 문장을 VERIFIED로 취급할 수 있다. 인용 전체와 의미가 확인된 범위를 분리해야 한다.
3. 같은 파일의 승인문서 분류: 문서 어딘가의 accelerated/traditional approval 단어만으로 해당 적응증의 승인 유형을 정하면 과거 서술을 현재 결정으로 오인할 수 있다. 결정문, 대상 적응증, 단독·병용, 날짜를 함께 확인해야 한다.
4. 같은 파일의 PMR와 후속 문서 연결: 날짜가 뒤라는 이유로 reports 관계를 만들면 실제 보고·이행 여부를 과장할 수 있다. PMR 식별자와 내용 근거를 요구해야 한다.
5. 약물 문서를 하나의 trial ID에 일괄 연결하지 않아야 한다. 같은 sotorasib라도 적응증·병용요법이 다르면 별도 가지로 관리한다. 기존 PLAN의 2025년 정식승인 표현은 NSCLC 단독요법의 승인 전환으로 확인되기 전 재사용하지 않는다.

테스트 통과와 과학적 신뢰성 사이의 간격을 메우는 것이 우선이다. 화면 완성도만 높이면 잘못된 연결이 더 신뢰감 있게 보일 수 있다.

## 본선 준비 우선순위

- P0: 위 다섯 정확성 문제의 실패 테스트와 교정. 출처 클릭이 아니라 출처가 실제 주장을 지지하는지 검증.
- P1: 최소 두 설계 후보 또는 생성 불가 사유, 고정 계산, 반론·수정·부분 보류를 한 실행으로 연결.
- P1: 정상·오류·결측의 독립 실행 예제 3개와 외부 접속 가능한 demo.
- P1: 전문가 주석 확보, 독립 평가 분리, 기준선과 기능 제거 실험. 목표 미달 시 실제 완료 범위 보고.
- P2: 기업 인터뷰에서 검토 패키지의 사용처, 검수 기준, 데이터 제공 범위와 유료 파일럿 의향 확인.

## 이름에 대한 판단

개정본에서는 기존 이름을 유지했다. TrialBoard는 회의용 검토 공간이라는 인상과 사업 확장성은 있지만, 이름만으로 용량 최적화 기능이 즉시 드러나지는 않는다. 당장은 “TrialBoard — 임상시험 용량 설계 근거 검토”라는 설명을 붙이는 편이 전면 변경보다 비용이 적다. 기능이 더 명확한 대안으로 DoseReview, TrialReview를 검토할 수 있으나 상표·도메인·유사 제품명은 조사하지 않았다. 이름 확정이나 상표 사용 가능성을 보장하지 않는다.
